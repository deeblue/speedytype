# SpeedyType 長錄音與 Hybrid 分段轉錄調查紀錄

- 日期：2026-07-16
- 範圍：8–9 分鐘真實錄音、未來最長 30 分鐘錄音
- 狀態：可行性測試完成，尚未套用至正式 daemon
- 參考專案：`C:\WORK\ConsoleOne\WebRTC`

## 1. 問題摘要

SpeedyType 計畫將單次錄音上限延長到 30 分鐘。現行錄音格式為 16 kHz、mono、PCM16 WAV，30 分鐘約為 54.9 MiB，會超過 Whisper 傳統轉錄請求的 25 MiB 上限。

除此之外，現行流程是在使用者停止錄音後才開始完整轉錄。實際三筆約 8–9 分鐘的錄音顯示，停止後仍需等待約 54–84 秒才完成整體處理。調查目標因此包含：

1. 找出長錄音安全送入轉錄 API 的方式。
2. 評估錄音進行中先處理已完成音訊，是否能降低停止後等待時間。
3. 確認音訊分段時不會在第一段關閉、第二段啟動之間漏音。
4. 確認分段轉錄結果不會因合併而缺句、重複或改變數字。

## 3. 方案一：細粒度 Hybrid／準串流分段

### 3.1 方法

錄音切成許多較短片段，在錄音期間陸續呼叫 Whisper，最後合併片段文字並與同輪完整 batch 結果比較。每筆錄音產生約 17–20 次請求，送出的總音訊量約為原音訊的 1.01 倍。

品質門檻包含：

- ordered coverage 至少 0.98；
- 不得缺少完整句；
- 不得新增重複句；
- 數字必須保留；
- 關鍵詞必須保留。

### 3.2 結果

| 錄音 | 同輪 batch | Hybrid | 時間改善 | Coverage | 缺句 | 重複 | 數字 | 結果 |
|---|---:|---:|---:|---:|---:|---:|---|---|
| A，522.860 秒 | 59.07 秒 | 61.81 秒 | -4.6% | 0.9076 | 51 | 2 | 失敗 | 不通過，需 fallback |
| B，480.324 秒 | 40.86 秒 | 55.33 秒 | -35.4% | 0.9182 | 29 | 2 | 失敗 | 不通過，需 fallback |
| C，480.324 秒 | 45.04 秒 | 19.36 秒 | +57.0% | 0.9525 | 19 | 0 | 失敗 | 實際不通過 |

第三筆曾被當時的內部 validator 誤判為通過，但依完整門檻重新檢視仍有缺句、coverage 不足與數字差異，因此不能接受。

### 3.3 判斷

細粒度方案 0/3 通過品質門檻，且前兩筆比完整 batch 更慢。過多短片段會增加模型輸出差異、上下文中斷、合併複雜度與 API 請求數，因此不採用為正式輸出流程。

## 4. WebRTC 參考專案調查

參考專案的主要設計位於：

`C:\WORK\ConsoleOne\WebRTC\acc_dock-main\app.py`

它採用以下方式：

- 錄製 48 kHz、mono、S16 WAV；
- 每 600 秒輪替一個 WAV 檔案；
- 錄音結束後依檔名排序；
- 同時啟動各 segment 的轉錄；
- 使用有順序的 `asyncio.gather` 收集結果；
- 串接文字後交給 GPT audio normalization。

### 4.1 可參考部分

- 麥克風輸入串流保持開啟，只輪替輸出檔案；
- 已封存的 segment 可以獨立轉錄；
- 結果必須依 segment index 組合；
- 保留原始 segment，方便失敗重試與稽核。

### 4.2 不宜直接照搬部分

- capture queue 滿載時會直接丟棄新 frame；
- 停止流程沒有明確保證先 drain 完 queue；
- GPT audio 多次拒絕時可能回傳空 segment，但整體流程仍繼續；
- normalization 可能修改內容，卻沒有完整性 validator；
- 轉錄實際上在錄音停止後才開始，不是真正的錄音中預處理；
- 48 kHz、10 分鐘 PCM WAV 約 54.9 MiB，若使用 Whisper 仍超過 25 MiB。

因此該 repo 提供了「持續錄音＋檔案輪替＋有序結果」的架構參考，但沒有完整解決漏 frame、停止時排空、檔案大小與文字品質問題。

## 5. 方案二：粗分段 Persistent Hybrid

### 5.1 方法

為降低細分造成的上下文問題，每筆錄音只在約 5 分鐘處的自然靜音切成兩段。第一段封存後即可開始 Whisper，錄音停止時只需等待第二段。

本輪使用精確 PCM sample index 離線切檔，未停止或重啟錄音裝置：

| 錄音 | 靜音區間 | 切點 | 第一段 frames | 第二段 frames |
|---|---|---:|---:|---:|
| A，522.860 秒 | 299.260–299.920 秒 | 299.590 秒 | 4,793,440 | 3,572,320 |
| B，480.324 秒 | 296.520–297.320 秒 | 296.920 秒 | 4,750,720 | 2,934,464 |
| C，480.324 秒 | 292.160–292.900 秒 | 292.530 秒 | 4,680,480 | 3,004,704 |

送出 API 前必須同時滿足：

1. 原始 PCM bytes 長度等於兩段 PCM bytes 長度總和；
2. 原始 PCM SHA-256 等於兩段依序串接後的 SHA-256；
3. 第二段第一個 sample 必須緊接第一段最後一個 sample；
4. 守恆檢查失敗時不得呼叫 API。

### 5.2 音訊交界安全結果

- PCM 樣本守恆：3/3 通過；
- 分段前後 PCM SHA-256 相同：3/3；
- 遺失 sample：0；
- 重複 sample：0；
- 測試後暫存 segment：0。

這證明「單一連續 PCM 流＋精確 sample 邊界」可以避免第一段關閉後出現約 1 秒的音訊空窗。正式實作不應停止第一個錄音器再啟動第二個錄音器，而應保持同一個麥克風 stream，只在 writer 內切換輸出檔案。

正式流程還必須在停止接收新 frame 後完整 drain queue，再關閉最後一段；queue 滿載時也不能像參考 repo 一樣靜默丟棄 frame。

### 5.3 速度結果

本輪每筆兩個 segment，共 6 次 Whisper 呼叫，沒有呼叫 Gemini。

| 錄音 | Segment 請求時間 | 完整 batch STT | 模擬即時分段停止後 STT | 改善 |
|---|---|---:|---:|---:|
| A，522.860 秒 | 16.57 + 11.76 秒 | 31.61 秒 | 11.76 秒 | 62.8% |
| B，480.324 秒 | 18.04 + 10.87 秒 | 21.85 秒 | 10.87 秒 | 50.3% |
| C，480.324 秒 | 16.88 + 9.51 秒 | 26.64 秒 | 9.51 秒 | 64.3% |

「模擬即時分段停止後 STT」假設第一段在錄音中已完成，並非正式 daemon 的端到端實測；它只代表可能的純 STT 尾端等待。

## 6. 目前結論

### 6.1 不採用

- 不採用細粒度 Hybrid 作為正式輸出；
- 不採用目前的兩段 Whisper 文字直接串接；
- 不採用停止／重啟錄音裝置的 segment 接力；
- 不直接複製 WebRTC repo 的 queue drop 與停止流程；
- 不允許 validator 失敗時仍靜默輸出分段文字。

### 6.2 可保留的架構元素

- 單一、不中斷的麥克風輸入 stream；
- 依精確 sample index 輪替持久化 WAV；
- 每段執行 PCM 守恆與雜湊驗證；
- segment 使用單調遞增 index；
- 已封存 segment 可在背景預處理；
- 停止時 drain 所有待寫 frame；
- 保留完整原始 WAV／segments；
- 任一 segment 空白、失敗或品質驗證不過時，完整 batch fallback。

### 6.3 目前最安全的 30 分鐘處理方案

在找到能穩定通過品質門檻的 Hybrid 合併方法前：

1. 持續保存 16 kHz mono PCM16 原始 WAV；
2. 停止後將超過 API 上限的錄音轉成暫存 64 kbps mono MP3；
3. 使用完整錄音執行一次 batch transcription；
4. 保留原始 WAV，暫存 MP3 可在成功後清除；
5. 轉檔或 API 失敗時保留音訊並顯示可理解的錯誤，不得遺失錄音。

此方案不能取得 Hybrid 預期的尾端加速，但目前最能維持完整錄音上下文與文字品質。

## 7. 測試限制與後續條件

- batch transcript 是同輪 Whisper 的比較基準，不是人工校訂 ground truth；
- Whisper 輸出具有非完全決定性，單次結果不能證明所有錄音都相同；
- 粗分段尾端時間是依錄音期間先處理第一段的模型推算，尚未整合 daemon 實測；
- 本輪沒有測試 macOS 實際長錄音中的即時檔案輪替；
- 本輪沒有修改 SpeedyType 正式程式碼；
- 若未來再測 Hybrid，至少仍須使用這三筆錄音，並維持 3/3 通過、coverage ≥ 0.98、零缺句、零新增重複句及數字保留等門檻。

在新的合併策略能通過上述條件前，粗分段只能作為研究或預處理資料，不能成為使用者最終文字來源。
